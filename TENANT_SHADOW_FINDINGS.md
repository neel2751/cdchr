# Shadow-mode findings — and how they were resolved

Generated by running the app in `TENANT_ENFORCEMENT=shadow` against a local
two-tenant database and invoking every read-shaped server action over HTTP with
a real session.

**Method.** Next.js server actions are dispatched by id, so they can be invoked
directly rather than through a browser: `POST /admin/dashboard` with a
`Next-Action: <id>` header and a JSON argument array. Ids come from
`.next/server/server-reference-manifest.json`, which also carries each action's
`filename` and `exportedName`. 91 read-shaped actions were driven this way (out
of 268 total); mutations, mail, and external-API actions were deliberately
excluded.

This matters because driving the pages with curl produces **nothing** — they
fetch through react-query after hydration, so the HTML response never invokes a
server action.

---

## Result 1 — no server action needs a tenant wrapper ✅

**Zero** "ran with no tenant context" warnings across all 91 actions.

Every query found its tenant through the session fallback in
`lib/tenantContext.js`. This confirms the Phase 2 decision to derive the tenant
from the request session rather than wrap 59 action files in `withTenant()` —
that work is not needed.

The escape hatches already in place (login, platform console, `/api/role`,
`/api/account/status`) cover the paths that legitimately have no session.

## Result 2 — `$lookup` is the whole of the remaining work ✅ *resolved*

18 warnings, all of one kind: a scoped root collection joining to an unscoped
one. `pre("aggregate")` can only filter the root; the join runs unfiltered
unless its own pipeline carries a tenant match.

Observed live:

| LeaveRequest | officeemployes | `getLeaveServer.js`, `leaveReportServer.js` |
| WeeklyRota | officeemployees *(see bugs below)* | `weeklyRotaServer.js:272` |
| Expense | companies, officeemployes, projectsites | `expenseServer.js` |
| ClockRecord | officeemployes, employees *(bug)* | `attendanceServer.js`, `attendanceReportServer.js` |

**Resolved by rewriting the stages at runtime rather than editing 81 sites.**
`lib/tenantPlugin.js` now transforms every `$lookup` inside `pre("aggregate")`,
so the conversion cannot be forgotten, cannot drift as new aggregates are added,
and covers the six sites that build the stage from a variable — which a
source-level edit could not reliably reach. The source is unchanged; the
behaviour is not. The shape it produces:

```js
// before — the join is unfiltered
{ $lookup: { from: "roletypes", localField: "department",
             foreignField: "_id", as: "departments" } }

// after — the join is scoped to the same tenant
{ $lookup: {
    from: "roletypes",
    let: { dep: "$department" },
    pipeline: [{ $match: { $expr: { $eq: ["$_id", "$$dep"] }, companyId: tenantId } }],
    as: "departments",
} }
```

The rewrite is careful about four things:

- **Global collections are left alone.** `companies`, `platformusers` and the
  auth-time collections have no `companyId`; adding a match would silently empty
  the join. Verified by test.
- **Array `localField` keeps Mongo's semantics** — an array matches if *any*
  element matches, so the generated `$expr` branches on `$isArray`.
- **Nested lookups are scoped at every level**, not just the outermost.
- **Already-scoped pipelines are not double-matched.**

Because the rewrite only applies under enforcement, shadow mode still reports
these joins — that is now expected output describing work already handled, not a
TODO list. Under `enforce` the warnings stop.

## Result 3 — three pre-existing bugs, unrelated to multi-tenancy ✅ *fixed*

The `$lookup` audit surfaced three joins naming collections **that do not
exist**. Mongo returns an empty array for an unknown collection rather than
erroring, so these have been silently returning nothing.

| Source | codes | actual collection |
|---|---|---|
| `server/weeklyRotaServer/weeklyRotaServer.js:272` | `officeemployees` | `officeemployes` |
| `server/reportServer/attendanceReportServer.js:52` | `employees` | `employes` |
| `server/siteAssignmentServer/siteAssignmentServer.js:450` | `employees` | `employes` |

Confirmed against the database: `officeemployees` = 0 documents,
`officeemployes` = 6.

The weekly-rota one resolves `approvedBy`, so the approver's details never
populate on the rota screen.

**Fixed**, on instruction. Verified against the production cluster before and
after — the weekly-rota `approvedBy` join went from **0 joined documents to 3**:

```
rotas with an approvedBy: 3
  OLD  from:"officeemployees" -> joined docs: 0
  NEW  from:"officeemployes"  -> joined docs: 3
```

A static check now confirms all 15 distinct `$lookup` targets in `server/` exist
as real collections in the database.

Expect the approver's name to start appearing on the weekly-rota screen, and the
two site-employee joins in attendance/site-assignment reports to start returning
rows. That is the bug being fixed, but it is a visible change.

## Coverage limits

- 91 of 268 actions driven — read-shaped only. Mutation paths have not been
  exercised and may hold further unscoped lookups.
- Driven as one role (`user`) in one tenant. Other roles reach other code.
- The static scan (81 sites) is the authoritative list; the 18 runtime warnings
  are the subset actually executed.

## Recommended order for Phase 3

1. Fix the three collection-name bugs — decide first whether the newly-returned
   data is wanted.
2. Convert the 81 `$lookup` sites, starting with `siteAssignmentServer.js` (30).
3. Re-run shadow mode; the lookup warnings should reach zero.
4. Run `npm run tenant:test` in both modes.
5. Only then set `TENANT_ENFORCEMENT=enforce`, and only after
   `npm run tenant:backfill` has run against the real database.

Three new isolation tests cover the join path specifically: a `localField` join
still resolves for its owner, a join pointed at another tenant's row returns
nothing, and a join into a global collection is *not* filtered.

### Not validated

Server actions could not be driven against the live cluster — that needs a real
login, which I do not have. The shadow re-run therefore covers the local
fixtures only. Driving the 91 read-shaped actions against production, signed in
as a real user, is worth doing before enforcement.
